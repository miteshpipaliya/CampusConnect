# Referral architecture
Preserve OTP registration, Firebase UID, session and server-only Firestore. New institutional accounts receive a server-maintained onboarding state in their profile creation transaction. Signed link cookies are resolved and copied into this state; manual entry uses the same atomic attribution transaction. Existing accounts are never opened for onboarding. Permanent code reservation lives in referralCodes; referral relationships use referred UID as document ID; a keyed email digest ledger prevents repeat enrollment across new UIDs. Lifetime stats and per-competition scores are updated in the same transaction. A singleton competition pointer serializes competition changes; scores are ordered by count descending, time reaching count ascending, document ID ascending. Admin APIs use existing custom-claim guard. All referral collections inherit deny-all Firestore rules. UI uses authenticated, no-store API polling, not direct Firestore access. No production changes until review.
## Setup and rollout
1. Deploy Firestore composite indexes from firestore.indexes.json in the correct Firebase project; wait until they are enabled. Existing firestore.rules deny every direct client read/write including all new collections.
2. Configure an optional stable server-only REFERRAL_SIGNING_SECRET of at least 32 characters (otherwise existing OTP_SIGNING_SECRET is used). Do not rotate the ledger key without a migration. Never put it in NEXT_PUBLIC_ variables. No new Firebase client setup or dependencies.
3. On /leaderboard, an existing Firebase admin custom-claim account can run the 50-user backfill repeatedly, processing each page until complete. The same idempotent reservation runs on new registration and sign-in. Review reported failures and repeat as needed. No existing user is eligible for retroactive attribution.
4. Create the competition with explicit start/end (up to 30 days). No default competition is invented. Server checks dates at every attribution. The admin can reconcile counts, disqualify with a reason, and finalize after the end; finalization recomputes scores from eligible relationships and freezes results. Export returns JSON. New competition can be scheduled after current finalization.
5. Verify two independent verified institutional accounts in an isolated Firebase test project before release. Check link flow, manual flow, invalid retry, skip, same student concurrent claims, existing users, privacy and admin authorization. CI unit/source tests do not prove live transaction contention or end-to-end email delivery.

## Operational limits and privacy
Only actual new Firebase accounts with verified institutional email may be referred; legacy orphaned Auth identities are deliberately not eligible. A 24-hour manual onboarding window is enforced server-side. Link capture expires after 30 days, and first valid cookie wins. Link pending state is persisted at registration and retried on authenticated bootstrap if processing fails. Code resolution requires active, verified owner. Test accounts are excluded from credit. The keyed institutional email ledger prevents repeat credit after deletion; it cannot identify accounts purged before this feature/ledger existed. Retain the minimal keyed ledger under a documented retention policy, review privacy requirements before rollout. No email, UID or private account metadata is exposed through normal leaderboard APIs. Private/blocked/deleted participants are redacted. Admin audit logs stay server-side.

The API uses 10-second visible-page polling, paginated ordered score queries and batched privacy/avatar hydration. Offset pagination and exact rank aggregation suit a small campus but incur additional reads at deep pages. Finalization is atomic and intentionally rejects more than 400 score documents or 5,000 referral records; larger competitions require staged reconciliation and a locked snapshot publisher. Suspicious patterns are reviewed by admin through real records; no automated device fingerprinting or App Check integration (server cookie architecture). No historical rank movement is fabricated. Existing auth session, rate limits and origin checks remain in place.

Administrators may flag or clear individual eligible referrals with a required reason. Finalization rejects unresolved flagged eligible referrals. Exports and mutations record audit events. Review is manual; no automatic fraud classifier is claimed.

## Short-code compatibility and leaderboard UI
New displayed codes use CC-XXXX with a random mixed uppercase alphanumeric suffix (1,212,640 possible mixed values: 36^4 - 26^4 - 10^4). Codes are public invite identifiers, not secrets. Transactional reservation and 32 bounded collision retries enforce unique ownership; the previous 128-bit code remains a valid alias. Existing verified accounts migrate idempotently at sign-in/bootstrap or via existing admin backfill. Both formats use the same signed cookie, eligibility transaction and rate limits. The shorter namespace is easier to enumerate; never use it for authentication or private lookup. Profile contains only a referral link button; /leaderboard?tab=referral hosts sharing and history. Rewards is enabled at /leaderboard?tab=rewards. No new Firestore indexes or variables are needed.
